# Secret and identity hardening

A single-place inventory of every secret and every identity this project
uses, end to end: GitHub Actions → Azure control plane → the running
Container Apps. Written after closing the one real gap that existed
(the Postgres password had no secrets manager behind it — see "Secret
rotation" below); the rest of this doc also just writes down decisions that
were already correct so they're recorded somewhere, not scattered across
commit messages and workflow comments.

Complements, rather than repeats,
[automated-azure-infrastructure.md](automated-azure-infrastructure.md)
(the CI/CD pipeline shape) and
[private-database-connectivity.md](private-database-connectivity.md) (why
Postgres has no public endpoint) — read those for the surrounding context.

## What secrets exist, and where they're stored

| Secret | What it protects | Where stored | Sensitive? |
|---|---|---|---|
| Postgres admin password | Full control of the dev database | Generated by Terraform (`random_password.postgres_admin` in [`environments/dev/main.tf`](../infra/azure/environments/dev/main.tf)) — never typed in by a human, never a GitHub secret. Lives as the server's actual live password (Azure-side) and inside Terraform state (see the state caveat below). | Yes — the one real credential in this system |
| `postgres-connection-string` | The password above, plus username/host/db name, as the connection string the backend actually uses | One secret in the dev Key Vault (`kv${project}${environment}<random-suffix>`, see [`modules/key_vault`](../infra/azure/modules/key_vault)). Nowhere else — not a Container App env value, not a workflow log, not a repo file. | Yes |
| `AZURE_CLIENT_ID_PLAN` / `_APPLY` / `_IMAGES` | Which Azure AD app registration a workflow authenticates as | GitHub Actions secrets. `_APPLY` specifically is scoped to the `dev-infra` **environment**, not the repo — only injectable into a job targeting that environment, i.e. one that's already passed (or is sitting behind) the required-reviewer gate. | Low — a client ID is a GUID, not a bearer credential; OIDC means there's no client *secret* to go with it. Stored as secrets anyway, out of caution, not necessity. |
| `AZURE_TENANT_ID` / `AZURE_SUBSCRIPTION_ID` | Which tenant/subscription to authenticate against | GitHub Actions (repo-level) secrets | Not sensitive on their own; stored as secrets mostly for consistency with the client IDs above |
| `REPO_VARS_PAT` | A fine-grained PAT, scoped to this repo only, `Variables: Read and write` and nothing else | GitHub Actions (repo-level) secret | Yes — a real bearer credential. Whoever holds it can set/read this repo's Actions variables, nothing more (can't touch code, secrets, or Azure). |
| Repo variables (`ACR_LOGIN_SERVER`, `BACKEND_IMAGE_TAG`, `FRONTEND_IMAGE_TAG`, `TF_STATE_*`, `AZURE_APPLY_SP_OBJECT_ID`, `AZURE_PLAN_SP_OBJECT_ID`\*, `AZURE_IMAGES_SP_OBJECT_ID`\*) | Nothing — these are non-secret identifiers/config | GitHub Actions repo variables (plaintext by design, not secrets) | No |
| Terraform state | The Postgres password and the Key Vault secret's *initial* value, in plaintext | `devnovacarttfstate01` storage account, `tfstate` container, `novacart-dev.tfstate` blob | Yes — see the caveat immediately below |

`AZURE_APPLY_SP_OBJECT_ID` (`novacart-github-apply`'s object ID, not its
client/application ID — the two are different Azure AD identifiers) is
actively read: every `terraform plan` invocation across the four
`terraform-*.yml` workflows passes it as
`-var="terraform_apply_identity_object_id=..."`. It exists because
`data.azurerm_client_config.current.object_id` can't stand in for it here
— see `terraform_apply_identity_object_id`'s description in
[`environments/dev/variables.tf`](../infra/azure/environments/dev/variables.tf)
for why the plan/apply identity split specifically breaks that data
source, and the Key Vault access-policy row below for what using it
without this variable actually did in production (granted the wrong
principal `Get` on the vault's secrets, so the *real* apply identity got a
403 reading the very secret Terraform had just told it to check).

\* `AZURE_PLAN_SP_OBJECT_ID`/`AZURE_IMAGES_SP_OBJECT_ID` were added, then
reverted, during a design discussion about Terraform-managing IAM role
grants directly — see "What was considered and rejected" below. Harmless
if still present; safe to delete.

**The Terraform state row is a real, acknowledged exposure surface**:
`sensitive = true` only redacts CLI/plan *output*, it has no effect on what
lands in state, so both the generated password and the Key Vault secret's
value sit there in plaintext. Mitigated by scoping who can read that blob —
both the plan and apply identities hold `Storage Blob Data Contributor` on
the `tfstate` **container** specifically (see
[automated-azure-infrastructure.md](automated-azure-infrastructure.md)),
not the whole storage account, and nobody else has any grant on it at all.
Treat the state file itself as a secret store: anyone who can read that
blob can read the Postgres password, full stop.

**Notably absent from the table above**: there is no
`TF_VAR_POSTGRES_ADMINISTRATOR_PASSWORD` secret anymore (removed — see
"Secret rotation"), no ACR admin username/password (`admin_enabled = false`
in [`container_registry/main.tf`](../infra/azure/modules/container_registry/main.tf) —
Container Apps pull images via managed identity, never a stored registry
credential), and no Azure client *secrets* anywhere (every GitHub→Azure
auth path is OIDC federated-credential, not a stored password).

**Nowhere in git**: no `.env` file exists in the repo (gitignored, and not
even present on disk locally); the only committed env-var reference is
`terraform.tfvars.example` with placeholder values;
`infra/azure/environments/dev/terraform.tfvars` (a real local file, if
present) is git-ignored (`*.tfvars`, with an explicit `.example` exception
in `.gitignore`). No hardcoded secret exists in any `.tf`, `.py`, or nginx
config file in this repo.

## How the application receives them

The backend ([`backend/app/main.py`](../backend/app/main.py)) does a plain
`os.getenv("DATABASE_URL")` — it has **zero** Key Vault awareness, no SDK
call, no extra dependency. The resolution happens entirely on Azure's side,
before the container ever starts:

1. The Container App's `secret` block (see
   [`modules/container_app/main.tf`](../infra/azure/modules/container_app/main.tf))
   is declared with `key_vault_secret_id` pointing at the Key Vault
   secret's *versionless* URI, plus an `identity` (the `keyvault_reader`
   managed identity — see below).
2. Azure Container Apps uses that identity to fetch the secret's current
   value from Key Vault and exposes it to the container as a normal `env`
   value under the name `DATABASE_URL`.
3. The app reads it like any other env var. If the underlying Key Vault
   secret's value changes later (see "Secret rotation"), the next
   revision picks up the new value automatically — no code change, no
   redeploy of a new image.

The frontend needs no secret at all: `BACKEND_INTERNAL_URL` (the backend's
internal FQDN) is a **plain** Container App env var, substituted into
`nginx.conf` via nginx's built-in envsubst
([`frontend/nginx.conf.template`](../frontend/nginx.conf.template)) — a
routing detail, not a credential.

## How deployment authentication works

Every GitHub→Azure authentication path is **OIDC federated-credential
based** — no long-lived Azure client secret is stored anywhere, in GitHub
or otherwise. Three separate app registrations exist, one per trust
boundary, rather than one shared identity, so that "what triggers this
workflow" and "what that workflow is allowed to do to Azure" line up
directly:

| Identity | Used by | Trigger it's trusted for |
|---|---|---|
| `novacart-github-plan` | `terraform-plan.yml`, the `plan` job of `terraform-apply.yml`/`terraform-destroy.yml`, `terraform-drift-check.yml` | Runs automatically, including on every PR — before human review |
| `novacart-github-apply` | The `apply`/`destroy` job only | Gated behind the `dev-infra` GitHub Environment's required-reviewer approval |
| `novacart-github-images` | `image-release.yml` | Push to `main` touching `backend/**`/`frontend/**`, or manual dispatch |

The federated credential on each app registration is scoped to a specific
GitHub subject (e.g. `repo:Geethu54/novacart:ref:refs/heads/main`), so even
knowing an app's client ID doesn't let an unrelated repo or branch
authenticate as it — Azure AD checks the incoming GitHub OIDC token's
claims against that exact subject before issuing anything.

Terraform's own state-backend authentication is a separate, orthogonal
detail (always the plan identity, regardless of which job is running) —
see "Backend auth vs. provider auth aren't the same thing" in
[automated-azure-infrastructure.md](automated-azure-infrastructure.md) for
why, rather than repeating it here.

## Which identities are used by which components

Two distinct layers — CI/CD identities (GitHub OIDC → Azure AD app
registrations) driving deployments, and Azure-runtime managed identities
letting already-deployed resources talk to each other:

**CI/CD:**

| Identity | Role(s) held | Scope |
|---|---|---|
| `novacart-github-plan` | `Reader` · `Storage Blob Data Contributor` · `Container App Secrets Reader` (custom) | Subscription · `tfstate` container only · `rg-novacart-dev` |
| `novacart-github-apply` | `Contributor` · `User Access Administrator` | Subscription · the ACR resource only |
| `novacart-github-images` | `AcrPush` | The ACR resource only |

**Azure-runtime:**

| Identity | Attached to | Role / access | Scope | Purpose |
|---|---|---|---|---|
| `id-${name_prefix}-acr-pull` | Both Container Apps | `AcrPull` | The ACR resource only | Pull container images at deploy/scale time |
| `id-${name_prefix}-kv-reader` | **Backend** Container App only | Key Vault access policy: `Get` (secrets) | The dev Key Vault only | Resolve `DATABASE_URL` at runtime |

The frontend Container App has no Key Vault identity attached at all — it
has no secret to read, so it isn't given the means to read one. This is
deliberate, not an oversight: see
[`environments/dev/main.tf`](../infra/azure/environments/dev/main.tf),
where `key_vault_identity_id` is only passed to `module.backend_app`.

## How access is limited to what the app actually needs

| Identity / component | Limited to | Blast radius if compromised |
|---|---|---|
| `novacart-github-plan` | Read-only everywhere, plus two narrow exceptions: `Storage Blob Data Contributor` on the `tfstate` container only (not the whole storage account), and the custom `Container App Secrets Reader` role — exactly one action, `Microsoft.App/containerApps/listSecrets/action`, nothing a built-in role offers at a narrower scope | Cannot create, modify, or delete a single Azure resource. This is precisely why it's safe to trust automatically on every PR, before any human has reviewed the diff. |
| `novacart-github-apply` | `Contributor` (real write power) plus `User Access Administrator` deliberately scoped to **only the ACR resource** — not the resource group, not the subscription | Can create/modify/delete anything in `rg-novacart-dev`, but cannot grant itself or anyone else IAM access outside that one ACR resource. Broadening this to subscription scope (even ABAC-constrained) was considered and rejected — see "What was considered and rejected." Tradeoff accepted instead: a from-scratch rebuild needs three manual Portal role grants each time (see the destroy/rebuild runbook in [automated-azure-infrastructure.md](automated-azure-infrastructure.md)). |
| `novacart-github-images` | `AcrPush` on the ACR resource only — no `AcrPull`, no secret access, no resource-creation rights | Could push a malicious image tag. Could not read the database credential, touch infrastructure, or grant itself more access. |
| Backend Container App's `kv-reader` identity | `Get` on one Key Vault secret, via an identity used for nothing else | Cannot list what else is in the vault, cannot read or write any other secret. Deliberately not the same identity as `acr-pull` — a compromise of one grants nothing on the other. |
| Key Vault's authorization model | Classic access policies (`rbac_authorization_enabled = false`), not Azure RBAC-based data access | RBAC-based access would need `Microsoft.Authorization/roleAssignments/write` on the vault — the exact permission kept narrowly scoped for the apply identity above. Access policies are a property of the vault resource itself, already covered by ordinary `Contributor`, so this design needed no new IAM grant at all — see [`modules/key_vault/main.tf`](../infra/azure/modules/key_vault/main.tf). |
| `REPO_VARS_PAT` | One permission (`Variables: Read and write`), this repo only, via a fine-grained PAT | Chosen because `GITHUB_TOKEN` has no scope that can write repository Actions variables at all, regardless of the workflow's own `permissions:` block — a fine-grained PAT was the narrowest thing that could do this one job. |

## Secret rotation, without a source-code change

The whole point of the Key Vault + generated-password design: rotating the
Postgres password touches no `.tf` file, no GitHub secret, and needs no
`terraform apply`.

1. Rotate the live server's password:
   ```bash
   az postgres flexible-server update \
     --resource-group rg-novacart-dev --name <server-name> \
     --admin-password <new-password>
   ```
2. Update the Key Vault secret to match (vault name from the
   `key_vault_name` Terraform output):
   ```bash
   az keyvault secret set --vault-name <key_vault_name> \
     --name postgres-connection-string \
     --value "postgresql://novacartadmin:<new-password>@<server-fqdn>:5432/novacart?sslmode=require"
   ```
3. Restart the backend's revision so it re-resolves the reference:
   ```bash
   az containerapp revision restart --name ca-novacart-dev-backend \
     --resource-group rg-novacart-dev --revision <latest-revision-name>
   ```

No step above touches this repository. Two `lifecycle` exemptions make
this safe against a *later*, unrelated `terraform apply` silently
reverting it:

- [`modules/postgresql/main.tf`](../infra/azure/modules/postgresql/main.tf):
  `ignore_changes = [..., administrator_password]` on the server resource.
- [`environments/dev/main.tf`](../infra/azure/environments/dev/main.tf):
  `ignore_changes = [value]` on `azurerm_key_vault_secret.postgres_connection_string`.

Without those two lines, the next apply would see Terraform state's
(now-stale) password value, diff it against the live rotated password, and
overwrite the rotation right back — a real footgun this design avoids
deliberately, not by accident.

The three OIDC identities don't have an equivalent rotation story, and
don't need one: federated credentials have no long-lived secret to expire
or leak in the first place. "Rotating" one of them means replacing the
federated credential's trust subject or the app registration entirely —
a rare, deliberate action (e.g. moving to a new repo), not a routine one.
`REPO_VARS_PAT` is the one exception that *is* a real bearer credential
with an expiry — rotating it means generating a new fine-grained PAT and
running `gh secret set REPO_VARS_PAT`, a manual step with no Terraform or
code involvement either.

## What was considered and rejected

Worth recording, since it's the kind of thing that looks like an oversight
until you know it was a deliberate call: this hardening pass also drafted
Terraform resources to let `novacart-github-apply` grant the `AcrPush` and
`Container App Secrets Reader` roles itself (removing the manual Portal
steps in the destroy/rebuild runbook entirely). Doing that required a
one-time, subscription-scoped `User Access Administrator` grant to the
apply identity, constrained via an ABAC condition to a fixed set of three
role definitions.

That constraint genuinely caps what the grant can be used for, but it
still broadens the identity's *reach* from one resource (the ACR) to every
resource in the subscription — a compromised apply run could, within the
three permitted role types, grant access to something entirely unrelated
to this project if the subscription ever hosts one. Weighed against the
convenience (skipping ~3 manual role grants per environment rebuild), the
call made here was to keep the narrower, resource-scoped grant and accept
the manual rebuild steps instead. The Terraform code for the alternative
was written, reviewed, and reverted rather than merged — if this tradeoff
gets revisited later, the condition JSON and role-definition IDs are cheap
to reconstruct (`AcrPull`: `7f951dda-4ed3-4680-a7ca-43fe172d538d`,
`AcrPush`: `8311e382-0749-4cb8-b61a-304f252e45ec`, and whatever object ID
`az role definition list --name "Container App Secrets Reader"` returns).
